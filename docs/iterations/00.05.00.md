# 00.05.00: email verification and account recovery

Status: development candidate; RELEASE BLOCKED. Reference #7. Baseline c6571ce9dcaf09919252fc086491f8bd4387fd00, unreleased 00.04.00. This is an additive feature-version increment, not completion of M01 or the previously proposed crypto milestone.

## Scope and user journeys

TB-009: after signup, open Account > Email verification and password recovery. When account mail is enabled, request verification; an encrypted creator-local database job sends an expiring signed link. Sign in to the matching account and follow the link. Email changes or password-reset generations invalidate previous links. Verification does not establish age, identity, ownership of depicted content or any administrator role. Existing entitlements and general-content access do not depend on verification.

TB-010: select Forgot your password, enter the site-local email and receive the same generic response regardless of account existence. Account lookup and delivery run in the worker, not on the public request path. Recovery links last 30 minutes; enter the email and a new password. Successful redemption consumes the hashed token, changes the password and session generation, rotates remember-token state and requires login again. Concurrent processing serializes on the user row on PostgreSQL; rollback must prevent partial resets. Pending mail requested before a completed reset is discarded. Reset does not automatically verify email or promote roles.

Partial TB-012: all authenticated web requests check a server-recorded user/generation stamp. Old, absent and mismatched stamps require fresh login, including previously entitled content and administrator routes. Requests already executing at reset time cannot be retroactively cancelled. Device listings and individual device removal, MFA and absolute/idle timeout controls remain unfinished.

## Configuration examples

Default CMS_ACCOUNT_MAIL_ENABLED=false keeps verification and reset submission unavailable rather than pretending mail was sent. No additional application dependencies are introduced.

Local mail sandbox: APP_ENV=local; APP_URL=http://localhost:8000; CMS_ACCOUNT_MAIL_ENABLED=true; MAIL_MAILER=smtp; MAIL_SCHEME=smtp; MAIL_HOST=127.0.0.1; MAIL_PORT=1025; MAIL_FROM_ADDRESS=noreply@example.test. Run a creator-controlled local SMTP capture service separately. Do not send these fixtures to real recipients.

Creator SMTP: APP_URL=https://creator.example; CMS_ACCOUNT_MAIL_ENABLED=true; MAIL_MAILER=smtp; MAIL_SCHEME=smtps; MAIL_HOST=<approved provider hostname>; MAIL_PORT=465; MAIL_USERNAME=<creator credential>; MAIL_PASSWORD=<creator secret>; MAIL_FROM_ADDRESS=<verified sender>; MAIL_FROM_NAME="Creator site". Store credentials only in private environment configuration. SMTP timeout is ten seconds. Certificate validation remains enabled. Outside local loopback, implicit TLS is required. An array mailer is permitted only in automated tests, never as an operational delivery claim. No mail-to-log driver is offered.

APP_URL must be an origin only, with no path, credentials, query or fragment. Enabled account email also enforces that incoming Host matches its configured hostname; proxy TLS and trusted forwarding require deployment-specific review. Mail URLs are built from the configured origin, never an incoming Host header.

Run migrations before starting the candidate. Start the creator-local worker with `php artisan queue:work database --queue=account-mail --sleep=1 --tries=3 --timeout=30`. Queue reservation retry_after=90 seconds; job retries back off 60 then 300 seconds. Jobs older than 15 minutes and disabled-mail jobs are discarded. Job bodies are encrypted with the creator's APP_KEY. Restart workers after code/config changes. Schedule `php artisan auth:clear-resets` hourly to purge expired reset records. Queue depth, mail health and worker alerting need operator integration before release.

## Privacy and diagnostics

New structured events: cms.mail.queued, cms.mail.processed, cms.mail.enqueue_failed, cms.mail.failed, cms.email.verified and cms.password.reset. Only typed actor IDs are retained where relevant. No email, password, link or SMTP message is logged by these handlers. Raw failed-job storage is disabled; final failure emits a safe event, so the user can request a new link. This trades detailed failure payloads for privacy. Infrastructure/web-server access logs must exclude query strings on reset/verification routes. SMTP providers necessarily receive recipient addresses and action links under the creator's own service agreement.

The site-local database contains verification/password timestamps, hashed reset tokens and encrypted queued jobs. Keep APP_KEY, database, backup and mail credentials private. Do not upload real account data, mail payloads or secrets into public CI artifacts.

## Compatibility and rollback

Breaking session behavior: existing sessions without a generation stamp must sign in again after upgrade. Account routes are additive; existing payment quote amounts, entitlements, classification restrictions and package lock are unchanged. No real checkout, media upload or restricted-content publication is enabled.

The new reversible migration adds three user columns and creator-local jobs/password_reset_tokens tables. Test rollback on a disposable clone: it preserves users/content but deletes queued mail, reset tokens and security timestamps. Stop workers first. Prefer a code rollback with the additive columns retained. Preserve the post-reset password hashes and invalidate all old sessions before any rollback to pre-generation code; do not restore revoked sessions or an old password backup. Keep APP_KEY and creator content. Re-enable only reviewed code/configuration. Never use the initial all-table destructive rollback against needed data.
