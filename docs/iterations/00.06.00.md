## Features and examples

A creator signs in, visits `/account/mfa`, confirms the current password and enters the displayed setup key into an authenticator. Use TOTP, SHA-1, six digits and a 30-second period. Pending enrollment expires after ten minutes. Confirmation requires the current password and a valid code. Ten 128-bit recovery codes appear once in the POST response; save them offline. They are stored only as SHA-256 hashes. No third-party QR service or external script sees the key. Pending and confirmed TOTP secrets use the framework's authenticated encryption under the creator's APP_KEY.

Administrators cannot manage content before enrollment and an MFA-verified session. Members can enroll too. Enrolled accounts are restricted to the challenge, logout and password-recovery routes until verification. Password reset preserves the factor and recovery codes. Recovery from an email account alone therefore cannot bypass MFA. Correct password plus one recovery code signs in; that code is deleted transactionally. Recovery-code rotation requires password plus an unused TOTP, invalidates the old set and displays a replacement set once.

TOTP matching allows the current 30-second step and one adjacent step on either side. The stored counter increases monotonically; an already consumed step is refused across sessions. A clock that is too far ahead can prevent subsequent codes until the server catches up. Keep server and device clocks synchronized. RFC vector and concurrent-consumption tests are included; these are not a substitute for independent cryptographic/security review.

`/account/sessions` shows only the member's current-generation, unexpired sessions, with creation/activity times in UTC. It deliberately omits IP addresses, raw user agents, cookies and fingerprints. A UUID row identifier manages a session but is not a bearer credential. Revoking another session preserves this session; revoking the current session logs out. Revoke-all increments the authentication generation and signs out every session. Password confirmation, CSRF and rate limits apply. Already executing responses cannot be recalled.

## Configuration and operational use

| Setting or command | Default / example | Meaning |
| --- | --- | --- |
| CMS_SESSION_IDLE_MINUTES | 30; permitted 5-120 | Reject a session at its idle deadline. |
| CMS_SESSION_ABSOLUTE_MINUTES | 720; permitted idle-1440 | Reject at maximum age even when active. |
| APP_KEY | Existing creator-owned key | Encrypts factor secrets and sessions/jobs; never replace it casually. |
| cms:security-prune | Run daily | Delete registry entries created more than seven days ago and clear expired pending keys and expired attempt budgets. Does not delete valid factors or accounts. |
| auth:clear-resets | Run hourly | Existing expired password-token cleanup. |

Changing timeout settings requires clearing/rebuilding configuration caches and restarting relevant processes. Invalid bounds fail startup. Shrinking a timeout can sign users out. All sessions created before the registry migration must sign in again. The configured database must be reachable on authenticated requests; failing closed is intentional.

To replace a lost authenticator, sign in with the password and a saved recovery code, open `/account/mfa`, and choose Replace authenticator within five minutes of that MFA verification. Confirm the password again. The old factor stays active until the new key is confirmed. Pending enrollment is bound to the current authentication generation and expires after ten minutes. Confirmation revokes other sessions and replaces all recovery codes. An abandoned replacement cannot disable the old factor. There is no public or email-only MFA-disable operation. Losing both the authenticator and all recovery codes currently requires a separately reviewed site-owner recovery procedure; do not bypass this by modifying database fields or restoring obsolete passwords/sessions. This operational recovery gap remains a release acceptance item. Provider verification and identity/age assurance are separate from account MFA.

## Atomic attempt limits

Authentication, MFA, recovery, verification, signup, reports and invoice writes consume creator-local SQL budgets instead of relying on non-atomic filesystem counters. Each budget stores an HMAC identifier, count and expiry, never the raw email/IP. The IP limit is evaluated before allocating account rows. Full transactions serialize concurrent consumption and have bounded retries. Database failure fails closed. A synchronized ten-process regression must allow exactly five requests in two distinct scenarios. Daily security pruning removes budgets that expired over one day ago. This adds the separate attempt_budgets migration and a database dependency to rate-limited public writes.

## Migration and rollback

Apply both new migrations, `2026_09_27_000003_add_mfa_and_sessions.php` and `2026_09_27_000004_add_attempt_budgets.php`, before activating new code. It adds seven factor fields, the recovery-code table and a session registry. The prior email/reset schema remains intact. Stop web/queue processes while changing versions and preserve APP_KEY, latest passwords, database and creator files.

The new migration's down method preserves core accounts/content but destroys factor/recovery/session metadata. Its execution is tested only on disposable databases. Prefer a forward fix or code rollback with additive columns retained. Reverting to old code can disable MFA enforcement; never reopen a public site on a pre-MFA version as an unreviewed workaround. Any emergency rollback requires maintenance mode, all sessions invalidated, a security-reviewed access restriction and preservation of the latest password hashes. Prior branch 00.05.00 is a recovery reference, not a safe public rollback target after enrolling factors.
